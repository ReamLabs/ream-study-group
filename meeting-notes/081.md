# Ream Meeting #81 Recap

## Overview

This week's call spanned memory and stability on long-running devnets, sync and consensus correctness fixes, execution-layer integration, aggregation topology, Shadow-simulation characterization, Kurtosis-based end-to-end beacon testing, data-availability work, and EPF-related contributions — including a new participant joining to work on black-box consensus testing.

## Development Progress

### Memory & Stability

- **Out-of-memory in devnets**: [Shariq] Digging into the issues Partha raised from his devnets, most of which are out-of-memory problems.
- **RAM-reduction flag & malicious-block stall**: [Soham] Found a feature flag that, when enabled, reduces ream's RAM consumption (following Derek's note last week that ream uses more RAM than ethlambda), and fixed an edge case where a validator authoring a malicious block could stall the chain — the PR merged a couple of days ago.
- **Lingering memory & CPU growth**: [Derek] With Soham's flag enabled, a lean-start run finalized to 7,500 slots, but memory still grows slowly and CPU usage creeps up over a six-node run until the machine can't keep up and finalization stalls; added a few optimizations to reduce lag/stalls, still to be tested.

### Sync & Consensus Correctness

- **Finalization stall → attestation-too-far-in-future**: [Kayden] A devnet finalized cleanly for ~900 slots then stalled; a PR Soham merged fixed that bug, but a follow-up run finalized fine for ~2,000 slots before failing with an "attestation too far in the future" error, which is now being investigated.
- **Tick-interval metric fix**: [Kayden] Fixed the tick-interval metric (flagged by Partha) that was reporting as intermediate rather than continuous.

### Execution-Layer Integration

- **Cross-node transaction propagation**: [Soham] Found the reth mempools weren't connected across nodes; exposed their P2P ports so nodes share TX mempools, and now has a devnet where a posted transaction gets included in a block and carried in the lean block.

### Aggregation Topology

- **Multi-subnet binary-tree topology**: [Unnawut] Focusing on subnets, where the slowness is; experimenting with eight subnets using a three-level binary-tree topology, which benchmarks as most performant (~1 second to aggregate two proofs into one). Continuing this week.

### Testing & Simulation

- **Shadow run characterization**: [Derek] More Shadow testing — six nodes across two subnets took ~7 hours of real time to simulate ~1h10m of runtime to reach 1,000 slots, so hosted runs will need an agreed finalization target (~1,000–2,000 slots). Shadow runs each ream node single-threaded (more deterministic), so one node per hardware thread is the best setup; the RAM flag can't help under Shadow since Shadow doesn't work with jemalloc and uses its own allocator, but per-client memory stays consistent at ~2.2 GB.
- **Kurtosis integration**: [Tosin] Worked on the Kurtosis integration for the beacon-client end-to-end test — implemented the Prometheus metrics needed for the Starlark code in the ethereum-package, and made changes to the ReamLabs fork of the ethereum-package; needs the fork-sync PR reviewed so the changes can be rebased cleanly against upstream.
- **End-to-end beacon test & EPF fork**: [Perfogic] Fixed and merged a leanSpec-test-workflow error, and worked with Hans and Tosin on the EPF cohort-7 research proposal — they'll create an organization and a ream fork, and open PRs from it once the end-to-end beacon test PR is reviewed and merged. This week: checking the Kurtosis integration for beacon-client bugs.
- **Black-box consensus testing proposal**: [Mohit] (new participant) Joining from EPF cohort 7 on black-box consensus testing (mentored by Kolby and Derek); researching XMSS key-lifecycle edge cases (crash mid-write leaving stale disk state, cloned-validator double-signing) and proposing tests for wrong-signing-index rejection, validator-index exhaustion, and cross-client aggregate verification at the root level (client A's multisig aggregate accepted by client B's verification code).

### Data Availability

- **Proposer data-column-sidecar broadcast**: [Hans] Continuing the PeerDAS plan for the beacon client via a PR to broadcast the data column sidecar from the proposer; found some beacon-client functions only follow Electra V4 rather than being fully compatible, with issues to be filed later.
- **Open PR review coordination**: [Kolby] Will review the open PRs today — the end-to-end block test — and DM to check whether the minimal DA (PeerDAS) availability client PR is ready for review.
